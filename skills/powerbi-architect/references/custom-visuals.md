# Custom visuals (.pbiviz) — last resort, built like a product

Only after the decision tree in SKILL.md §4 and an ADR (template in `visual-selection.md`).
A custom visual is software the organization must maintain, certify and upgrade.

## 1. Toolchain
- Node.js LTS + `npm i -g powerbi-visuals-tools` (CLI `pbiviz`, v7.x at the time of writing).
- `pbiviz new <name>` → scaffold (generates a unique GUID in `pbiviz.json`).
- `pbiviz start` → dev server; enable *Developer visual* in Power BI Service settings to debug live.
- `pbiviz package` → `dist/<guid>.<version>.pbiviz` (runs ESLint with `eslint-plugin-powerbi-visuals`
  and reports missing recommended features).
- Recent tool versions also ship `pbiviz mcp` (an MCP server for visual development); new projects
  include `.vscode/mcp.json` wiring it.
- API: `powerbi-visuals-api` 5.x (`apiVersion` in `pbiviz.json`). Use the version generated by the
  installed tools; don't hand‑edit to a newer one.

## 2. Project layout
```
visuais-customizados/<name>/       (Power BI Workspaces) or <project>/visuals/<name>/
├── pbiviz.json                    name, displayName, GUID, version, author, support/GitHub URLs
├── capabilities.json              data roles, mappings, objects, feature flags
├── package.json · tsconfig.json · eslint.config.mjs
├── src/visual.ts                  IVisual implementation
├── src/settings.ts                formatting model (cards/slices)
├── style/visual.less
├── stringResources/<locale>/resources.resjson
└── assets/icon.png                20×20
```
The packaged file goes to `3-entrega/<name>.pbiviz` (Power BI Workspaces) — source is versioned, `node_modules`
and `.tmp` are not.

## 3. Reference implementation
`templates/pbiviz-bullet-kpi/` in this skill is a complete, **verified** visual (actual vs target per
category). It type‑checks, passes the official ESLint config and packages with **no recommended
feature missing**: rendering events, landing page, selection/multi‑select, context menu, tooltips
(+ tooltip role), highlights, localization (en‑US, pt‑BR), keyboard focus, high contrast,
`allowInteractions`, formatting model, no network.

Start a new visual like this:
```bash
cd visuals && pbiviz new myVisual          # real GUID + toolchain
cp -r <skill>/templates/pbiviz-bullet-kpi/{src,style,stringResources,capabilities.json} myVisual/
cd myVisual && npm i d3-selection d3-scale @types/d3-selection @types/d3-scale
# fill author/description/supportUrl in pbiviz.json, then adapt the code
npm run lint && pbiviz package
```

## 4. Mandatory capabilities (capabilities.json)
```json
"supportsLandingPage": true,
"supportsEmptyDataView": true,
"supportsKeyboardFocus": true,
"supportsHighlight": true,
"supportsMultiVisualSelection": true,
"tooltips": { "supportedTypes": { "default": true, "canvas": true }, "roles": ["tooltips"] },
"privileges": []
```
`privileges: []` = no web access, no local storage, no downloads. Requesting `WebAccess` makes the
visual uncertifiable and is blocked by most tenants — don't.

## 5. Data mapping
- Prefer `categorical` mapping with explicit `conditions` (`max: 1` per role) — it prevents nonsense
  field combinations and simplifies code.
- `dataReductionAlgorithm` (`top`/`window`) caps rows; use `fetchMoreData` only when truly needed.
- Read values by **role**, not by index: `values.filter(v => v.source.roles["actual"])`.
- Format numbers with the column's `format` (`valueFormatter` from `powerbi-visuals-utils-formattingutils`)
  when users expect the model's formatting.
- Handle `null`, empty categories, negative values, a single row, thousands of rows.

## 6. Formatting model
- `powerbi-visuals-utils-formattingmodel`: `SimpleCard`/`CompositeCard` with slices (`ColorPicker`,
  `ToggleSwitch`, `NumUpDown`, `FontControl`, `ItemDropdown`…). Each card `name` and slice `name` must
  match `capabilities.json › objects`.
- Defaults neutral (theme‑friendly). Few options, well named. Use `topLevelSlice` for on/off cards.
- `populateFormattingSettingsModel` in `update`; `buildFormattingModel` in `getFormattingModel`.

## 7. Interactivity
- `host.createSelectionManager()`; ids from `host.createSelectionIdBuilder().withCategory(cat, i)`.
- Click = select; Ctrl/Cmd+click = multi‑select; click on empty space = clear;
  `registerOnSelectCallback` to sync bookmarks; `showContextMenu` on right‑click (data point and empty area).
- Tooltips: `host.tooltipService.show/move/hide` with `identities` (enables report page tooltips) and the
  `tooltips` data role.
- Highlights: read `column.highlights` and draw highlighted vs total.
- `host.hostCapabilities.allowInteractions === false` → render read‑only.
- Drill‑down / `launchUrl` / `downloadService` only if the ADR asks for them.

## 8. Accessibility
- `supportsKeyboardFocus`; focusable elements with `tabindex=0`; Enter/Space select; visible focus ring.
- ARIA: `role="list"`/`listitem` or appropriate roles, `aria-label` with category + values, `aria-selected`.
- High contrast: `host.colorPalette.isHighContrast` → use `foreground`, `background`,
  `foregroundSelected`, `hyperlink`; no information by color alone.
- Text ≥ 10 px; respects theme fonts when possible.

## 9. Security (certification‑grade)
- No network calls (`fetch`, `XMLHttpRequest`, WebSocket, external fonts/scripts/CDNs).
- No `eval`, `new Function`, `setTimeout(string)`; no `innerHTML`/`outerHTML` with any data —
  use `textContent` / d3 `.text()`.
- Sanitize everything that comes from data before rendering URLs (`powerbi-visuals-utils-…` helpers).
- `npm audit` clean; pin dependencies; minimal dependency tree (import `d3-selection`, `d3-scale`, not all of `d3`).
- No telemetry, no local storage of data.

## 10. Performance
- Data‑join once (`selection.join`) — never clear and redraw everything on each update.
- Avoid layout thrash; compute scales once per update; throttle `mousemove` work.
- Call `eventService.renderingStarted/Finished/Failed` in every `update` (required for exports
  and performance tracking).
- Cap rows; aggregate in DAX instead of in the visual.

## 11. Testing & packaging
- `npm run lint` (official config) and `tsc --noEmit` must be clean.
- Manual matrix: empty data · 1 row · 1 000 rows · nulls · negatives · long labels · small viewport ·
  high contrast · keyboard only · cross‑filter in/out · export to PDF/PPT · mobile layout.
- `pbiviz package` with no *recommended* warnings; bump `version` in `pbiviz.json` (4 parts) on every change.

## 12. Distribution
| Option | When |
|---|---|
| Import `.pbiviz` into the report | prototypes, single report |
| **Organizational visuals** (admin portal) | the normal enterprise route: central version control |
| AppSource + certification | public distribution (requires public source, review by Microsoft) |

Record version and distribution in `ficha.toml › [design] custom_visuals` and in the decision record.

## 13. Review checklist
- [ ] ADR proves no native/AppSource option fits
- [ ] Landing page, rendering events, keyboard, high contrast, tooltips, context menu, highlights
- [ ] `privileges: []`, no network, no innerHTML/eval, `npm audit` clean
- [ ] Localized strings (at least en‑US + project language)
- [ ] Lint + typecheck clean, package without recommended warnings
- [ ] Source in `trabalho-da-ia/visuais-customizados/<name>/`, package in `3-entrega/`, version bumped, owner named
